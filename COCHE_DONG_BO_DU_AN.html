Cơ chế Backup & Đồng bộ Dữ liệu Case Study (KTPMUD) ​

Tài liệu thiết kế nội bộ — không xuất bản lên trang VitePress công khai (không nằm trong sidebar/nav của docs/.vitepress/config.mts). Ngày thiết kế: 13/09/2026. Áp dụng cùng nguyên tắc với Sach_HocMayYTe/docs/COCHE_DONG_BO_DU_AN.md, mở rộng thêm 1 tầng phân nhóm theo domain để chịu được quy mô lớn hơn (xem mục 2).

1. Vấn đề cần giải quyết ​

Trước khi có cơ chế này, mục "0. DANH MỤC CASE STUDY" trong docs/do_an_mon_hoc.md là 1 bảng Markdown viết tay, tĩnh — mỗi case study (CS-1, CS-2, CS-3...) là 1 dòng văn bản trực tiếp trong file. Cách làm này có 2 rủi ro, đặc biệt nghiêm trọng khi số lượng case study tăng lên theo thời gian (mỗi chuyên khoa lâm sàng mới lại sinh thêm case study):

  1. Va chạm ghi đè. Toàn bộ case study nằm trong 1 file duy nhất — sửa case study A có thể vô tình làm hỏng định dạng bảng của case study B nằm ngay dòng kề bên. Đây chính là lỗi đã xảy ra ở dự án song song Sach_HocMayYTe (ghi đè nhầm giữa các đề tài), nên được phòng ngừa ngay từ đầu ở đây.
  2. Không co giãn theo quy mô. 1 bảng phẳng còn quản lý được với 3 case study, nhưng khi tăng lên hàng chục case study trải nhiều chuyên khoa (tim mạch, thần kinh, da liễu, nhãn khoa, hô hấp...), 1 bảng phẳng dài trở nên khó rà soát, khó biết case study nào thuộc chuyên khoa nào, và dễ trùng lặp/mồ côi.

2. Kiến trúc cây (khác với Sach_HocMayYTe ở tầng phân nhóm) ​

Sach_HocMayYTe dùng cấu trúc phẳng (1 file JSON/đề tài, gom nhóm theo số group cố định 1-4). KTPMUD dùng cấu trúc cây 2 tầng vì đặc điểm tăng trưởng khác nhau: case study mới thường đến kèm 1 miền nghiệp vụ lâm sàng mới (domain), không chỉ thêm vào nhóm số cố định.

Sach_KyThuatPhanMemUngDung/
├── kich_ban_thuc_hien/                          ← NGUỒN SỰ THẬT (tài liệu chi tiết)
│   ├── kich_ban_do_an_ai_cdss_suy_tim.md
│   ├── kich_ban_do_an_ai_cdss_alzheimer.md
│   └── kich_ban_do_an_<slug_moi>.md             ← case study mới thêm vào đây
│
├── docs/data/case_studies/                      ← TẦNG HIỂN THỊ, dạng CÂY
│   ├── da_lieu_mien_dich/
│   │   ├── _domain.json                         ← { label, icon, order }
│   │   └── may_day.json                         ← CS-1 (case study)
│   ├── tim_mach/
│   │   ├── _domain.json
│   │   └── suy_tim.json                         ← CS-2
│   ├── than_kinh_lao_khoa/
│   │   ├── _domain.json
│   │   └── alzheimer.json                       ← CS-3
│   └── <domain_moi>/                            ← thêm domain mới = thêm 1 thư mục
│       ├── _domain.json
│       └── <case_moi>.json
│
├── docs/data/case_studies.data.js               ← LOADER VitePress (quét cây + validate)
│
└── docs/do_an_mon_hoc.md                        ← "Mục 0" render bằng v-for lồng 2 tầng

2.1. docs/data/case_studies/<domain>/_domain.json — metadata 1 miền ​

json
{ "label": "Thần kinh & Lão khoa", "icon": "🧠", "order": 3 }

Bắt buộc: label. order quyết định thứ tự hiển thị (domain chưa có order mặc định xếp cuối).

2.2. docs/data/case_studies/<domain>/<case>.json — 1 case study ​

json
{
  "id": "CS-3",
  "title": "AI-CDSS Alzheimer",
  "context": "Phòng khám Trí nhớ BV Hữu Nghị, sàng lọc & điều trị Sa sút trí tuệ",
  "technical_highlight": "Phân tích xu hướng suy giảm MMSE/MoCA...; DDI-AI tính gánh nặng kháng Cholinergic tích lũy (ACB≥3)",
  "difficulty": "Khá–Giỏi",
  "doc_link": "https://github.com/fossbk-spec/KTPMUD/blob/main/kich_ban_thuc_hien/kich_ban_do_an_ai_cdss_alzheimer.md",
  "doc_link_type": "external",
  "doc_link_label": "Xem trên GitHub ↗"
}

Trường bắt buộc: id, title, difficulty, doc_link. doc_link_type là 1 trong 3 giá trị:

  • "anchor" — case study viết inline ngay trong docs/do_an_mon_hoc.md (trường hợp legacy của CS-1 "Dr May Day", neo #cs-1-dr-may-day). Case study mới không nên dùng kiểu này — luôn tạo file riêng trong kich_ban_thuc_hien/ để giữ cách ly.
  • "external" — trỏ tới file .md riêng trong kich_ban_thuc_hien/ qua URL GitHub blob (kiểu khuyến nghị cho mọi case study mới).
  • "internal" — dự phòng cho trường hợp trỏ tới 1 trang /du_an/... được build sẵn trong chính site VitePress này (chưa dùng, nhưng loader/audit script đã có chỗ mở rộng).

2.3. docs/data/case_studies.data.js — loader quét cây + validate ​

VitePress data loader, đọc đệ quy docs/data/case_studies/:

  • Tự phát hiện danh sách domain qua fs.readdirSync (không có danh sách domain cố định trong code) — thêm domain mới không cần sửa loader.
  • Chặn build nếu: domain thiếu _domain.json/label, case JSON lỗi cú pháp, thiếu trường bắt buộc, hoặc trùng id giữa 2 case bất kỳ trên toàn bộ cây (không chỉ trong cùng domain).
  • Sắp xếp domain theo order, case theo id (tự nhiên).
  • Khai báo watch: ['case_studies/**/*.json'] để dev server tự rebuild khi bất kỳ file nào trong cây đổi.

2.4. docs/do_an_mon_hoc.md — v-for lồng 2 tầng ​

vue
<script setup>
import { data as caseStudies } from './data/case_studies.data.js'
</script>

"Mục 0" giờ là <div v-for="domain in caseStudies.domains"> (vòng ngoài, 1 bảng/domain) lồng <tr v-for="c in domain.cases"> (vòng trong, 1 dòng/case study). Không còn văn bản tĩnh của case study nào trong file này.

3. Vì sao cây này chịu được tăng trưởng "gấp nhiều lần" ​

Yêu cầuCách kiến trúc cây đáp ứng
Cách ly képSửa 1 case study chỉ chạm 1 file. Thêm domain mới chỉ tạo 1 thư mục — không đụng domain khác.
Backup/lịch sử theo từng cấpgit log -- docs/data/case_studies/tim_mach/ cho lịch sử toàn bộ domain Tim mạch; git log -- .../suy_tim.json cho lịch sử riêng 1 case study.
Không có danh sách cố định phải sửaDomain được phát hiện qua quét thư mục — không có enum/switch-case nào trong code liệt kê tên domain phải cập nhật khi thêm mới.
Phát hiện lỗi sớm, đúng vị tríLỗi báo kèm đường dẫn tương đối <domain>/<file>.json — tìm và sửa tức thì, không cần dò cả cây.
Đối chiếu nguồn thật ↔ tầng hiển thịscripts/audit_case_studies.py phát hiện case study mồ côi (JSON không trỏ tới file thật trong kich_ban_thuc_hien/) và file mồ côi (có file .md nhưng không case study nào tham chiếu).

4. Quy trình thêm case study mới đúng cách ​

  1. Viết tài liệu chi tiết đầy đủ: kich_ban_thuc_hien/kich_ban_do_an_<slug>.md (theo đúng cấu trúc 12-chương mapping như CS-2/CS-3 hiện có).
  2. Xác định case study thuộc domain nào:
    • Nếu domain đã tồn tại (tim_mach, than_kinh_lao_khoa, da_lieu_mien_dich) → tạo file JSON mới trong thư mục đó.
    • Nếu là domain mới (vd nhan_khoa, ho_hap) → tạo thư mục mới + _domain.json ({"label": "...", "icon": "...", "order": N}) + file case study JSON.
  3. Điền JSON case study theo schema mục 2.2, doc_link_type: "external", doc_link là URL GitHub blob trỏ tới file bước 1. Đảm bảo id (vd "CS-4") chưa tồn tại ở bất kỳ domain nào.
  4. (Tùy chọn) Nếu case study cần trang menu/sidebar riêng, thêm mục vào docs/.vitepress/config.mts.
  5. Chạy kiểm tra:
    python scripts/audit_case_studies.py
npm run docs:build
    Cả 2 phải PASSED/thành công trước khi commit.

5. Kiểm tra tự động sẵn có ​

Công cụKhi nào chạyPhát hiện gì
docs/data/case_studies.data.jsMỗi lần npm run docs:build / docs:devDomain thiếu metadata, JSON lỗi cú pháp, thiếu trường bắt buộc, trùng id toàn cây
scripts/audit_case_studies.pyChạy thủ công trước khi commitTrên + doc_link external trỏ tới file không tồn tại, file kich_ban_thuc_hien/*.md mồ côi

Cả 2 đã được kiểm thử bằng cách cố tình tạo lỗi (file case study trùng id ở 2 domain khác nhau) và xác nhận báo lỗi đúng, chính xác 2 đường dẫn xung đột, không làm hỏng các case study khác.
